# Composable service workspaces

**Use one versioned `.keiro-workspace` manifest whenever a service keeps complete aggregates in separate `.keiro` files; run every file-taking command against that manifest.**

A workspace is one service contract, not a collection of independently generated specs. It preserves per-aggregate source ownership while composing shared declarations, validation, generated modules, scaffold history, compatibility findings, replay impact, and coverage into one deterministic service graph.

## Choose the source layout by review boundary

Keep a small, densely connected service in one `domain/<service>.keiro` file. Use a workspace when complete aggregates need separate review ownership, the repository already keeps one aggregate per file, or several same-context specs would otherwise scaffold into the same output tree.

The layouts are semantically equivalent. A bare `.keiro` input remains supported as a one-member service. Splitting whole aggregates into members later is a source-ownership move; it does not create a new wire identity or justify renaming generated modules.

Do not scaffold same-context members independently. Context-keyed legacy records overwrite one another, each invocation sees only a partial graph, and each may rewrite a context-level facade from incomplete information.

## Make the manifest the service authority

Version the manifest beside its members and list every member relative to the manifest directory:

```text
service demo-project
module Demo.Modules.Project
layout collocated
spec project-artifact.keiro
spec project.keiro
spec shared.keiro
```

The rules are strict:

- `service` is the stable workspace identity and the key for scaffold history and reports.
- Every member is a complete, independently parseable `.keiro` spec and declares the same `context`.
- Every member selects the same effective language version. Composition compares versions before merging the graph and refuses a disagreement with `WorkspaceLanguageVersionMismatch`; move the whole workspace across a version in one change. See [Keiro DSL language versions](language-versions.md).
- Aggregates are never split across members. Shared ids, enums, rules, and mapped declarations have exactly one owning member; even textually identical duplicates are refused.
- A manifest `module` or `layout` clause is authoritative. A member may omit that clause or repeat it exactly, but may not disagree. Without a manifest clause, declared member values must agree unanimously.
- Member paths are relative `.keiro` paths with no absolute or `..` segments, nested manifests, duplicates, or case-fold collisions. Membership is a set: canonical path order, not manifest order, determines composition and generated bytes.

Put shared declarations in a clearly owned member such as `domain/shared.keiro`. Do not copy declarations into every aggregate file and do not introduce textual includes.

## Operate on the composed service

Pass the manifest anywhere the CLI accepts a file:

```bash
keiro-dsl parse domain/service.keiro-workspace
keiro-dsl check domain/service.keiro-workspace --explain-bindings \
  --coverage-report build/keiro-coverage.json
keiro-dsl scaffold domain/service.keiro-workspace --out service-core/src
keiro-dsl diff domain/service.keiro-workspace --since HEAD^ --explain \
  --report-out build/keiro-diff.json \
  --replay-impact-out build/replay-impact.json
```

`parse` and `check` resolve cross-member references and report diagnostics at the original member path and line. `scaffold` plans the complete member set before writing, emits context-level modules such as `StructuralProjections` and replay-audit assembly exactly once, and refuses any parse, validation, lowering, collision, cycle, or banner failure before the first output byte changes.

Reordering `spec` lines and repeating an unchanged scaffold must produce byte-identical output. Generated modules are reported as `unchanged`; create-once holes and bindings are `skipped`.

## Keep workspace-keyed, attributable history

A workspace scaffold writes:

```text
keiro-dsl-scaffold-record.workspace.<service>.txt
keiro-dsl-manifest.workspace.<service>.txt
```

The record attributes aggregate-owned modules to their member and marks service-wide modules as context-level. Moving an aggregate or declaration between members is an ownership move, not stale/new churn. The single-file context-keyed record names remain unchanged for compatibility.

Stale reports are advisory and Keiro never deletes files. Review stale generated files, hand-owned holes, and unclaimed files separately; delete or rename only after a human establishes ownership.

## Adopt existing output without weakening the firewall

To adopt one existing multi-aggregate file, create a one-member manifest and scaffold it. Split whole aggregates later, moving each shared declaration to exactly one owner.

To adopt output produced by independent same-context scaffolds, keep the existing tree and run one workspace scaffold. On the first run, Keiro claims only attributable generated output:

- `record` evidence means the file appears in the surviving legacy context record;
- `banner` evidence means an orphaned planned Generated file carries the exact generated banner;
- holes, unrelated hand-written files, and likely-stale paths remain unclaimed.

The run writes `keiro-dsl-migration-report.workspace.<service>.txt`, appends a forward-compatible `superseded-by:` marker to the legacy record, and records claim provenance. It deletes and renames nothing. A bannerless file at a planned Generated path refuses the whole run without changing the tree.

Consolidate golden payloads under one workspace root before adoption. Golden paths are aggregate-keyed, so moving an aggregate between members must not move or silently replace its historical fixtures.

## Diff the historical workspace, not today's member list

`diff` reconstructs both the old manifest and its old member set from Git. It emits one compatibility stream, one coverage report, and one replay-impact verdict for the service. A shared declaration change is classified at every aggregate use site with both the declaration owner and the consuming member cited.

Moving unchanged declarations or aggregates between members emits `OwnershipMoved` and requires a whole-workspace rescaffold; it is not wire evolution. Changes to service, context, module, or layout authority emit `WorkspaceAuthorityChanged` beside any actual persisted-identity findings. Automation branches on diagnostic codes, never rendered wording.
