# Semantic-local Keiro DSL regeneration

**Regenerate from the checked dependency graph, keep source positions out of semantic identity, and review semantic impact separately from changed files.**

This contract shipped in Keiro 0.12.0.0 and is fixed by `mori://shinzui/keiro/masterplans/34-make-keiro-dsl-regeneration-semantically-local-and-source-stable-before-wide-adoption`. It is a property of the generator; do not reproduce any part of it in application scaffolding.

## Establish the new generated baseline once

Regenerate each service exactly once when adopting this contract. Repaste the Cabal fragment so the runtime package compiles the context-level `StructuralConformance` and `BehaviorSourceMap` modules, then run the generated service conformance target.

Accept the additive `semantic-impact` ledger row as a new evidence baseline. A legacy ledger has no historical semantic snapshot; its first report must say that the baseline is unavailable rather than pretending the old consumer set was empty. The layout migration does not by itself change wire, fold, snapshot, or behavior-key identities.

## Put each law at its real ownership boundary

`StructuralConformance` owns declaration-wide binding round trips, canonical identities, fixture labels and branch coverage, opaque-boundary evidence, and structural projection witnesses exactly once for the service. It includes intentionally unused mapped declarations.

An aggregate harness owns only the command, private-event, register, workqueue, read-model-query, and aggregate-derived projection consumers reachable through its checked semantic closure. Adding an unrelated member, aggregate, or consumer must not add imports or byte churn to that harness.

Finite fixtures remain evidence, not a total proof of a consumer binding. Keep public integration contracts, arbitrary application SQL, and heterogeneous category/all projection sources explicit as unsupported inference boundaries.

## Keep source movement out of semantics

Stable behavior keys identify obligations. The context `BehaviorSourceMap` resolves each key to its current file, line, and column. Generated behavior contracts and create-once witness comments must not embed positions that go stale when source moves.

Moving an otherwise unchanged state or transition may rewrite `BehaviorSourceMap` and source-bearing ledger provenance. It must not change the stable key, behavior contract, witness, fold fingerprint, runtime semantics, or mapped semantic impact. A failure resolves the key through the current map before reporting its location.

For workspaces, compose member source indexes after canonical path resolution and reject duplicate, missing, unexpected, or file-mismatched semantic subjects. Source ownership may move; semantic identity does not.

## Read two impact reports, not one

Treat scaffold and diff output as two independent projections:

- `semantic impact` names checked mapped consumers, roots, durable consequences, and the service structural-conformance role;
- `generated-artifact impact` names bytes that changed, distinguishing aggregate output, `StructuralConformance`, and `BehaviorSourceMap`.

A changed file is not evidence of a semantic consumer, and a semantic consequence is not cleared merely because generated bytes stayed stable. Review both before accepting regeneration.
